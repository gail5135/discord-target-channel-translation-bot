## 1. 배경과 범위

Phase 3까지 번역은 동작하지만 게시가 봇 명의다. 작성자 이름은 본문 첫 줄에 굵게 들어간다.

```
dev-channer-translation-bot [앱]
**YomaNezz**
FF14 이외의 모집 채널도…
```

이것이 이 프로젝트의 핵심 차별점(CLAUDE.md 첫 문단)이 아직 구현되지 않은 상태다. Phase 4는 전송 계층을 Webhook으로 바꿔 이름과 아바타를 원 발신자의 것으로 만든다.

```
YomaNezz [앱]
FF14 이외의 모집 채널도…
```

함께 첨부파일 전달도 넣는다. Phase 3은 본문 없는 메시지를 건너뛰므로 이미지만 올린 게시물이 미러 채널에서 통째로 사라진다.

**범위 밖**: pm2 배포와 에러 핸들링 정비(Phase 5).

## 2. 설계 결정

### 2.1 Webhook 토큰을 디스크에 저장하지 않는다

**결정**: `config.json`에 Webhook 정보를 저장하지 않는다. 출력 채널별 Webhook은 **메모리 Map**에만 보관하고, 봇 재시작 시 다시 조회·생성한다.

절차:

1. 메모리 Map에 있으면 사용
2. 없으면 `channel.fetchWebhooks()`로 **봇이 소유한** Webhook(`owner.id === client.user.id`)을 찾음
3. 없으면 `channel.createWebhook()`으로 생성
4. Map에 보관

**근거**: 개발 계획서 §4의 원래 데이터 모델은 `webhookCache: { [channelId]: { webhookId, webhookToken } }`를 두었으나, Phase 2 최종 리뷰에서 **Webhook 토큰이 살아있는 자격증명**이라는 점이 지적되었다. id와 토큰만 있으면 봇 인증 없이 그 채널에 임의 명의로 게시할 수 있고 만료도 없다. 그래서 그 문서는 "토큰을 아예 저장하지 않는 방안은 Phase 4 착수 시 재검토한다"로 결론을 미뤄두었다. 지금이 그 시점이다.

저장하지 않는 비용은 **출력 채널당 봇 재시작 1회의 API 호출**뿐이다. 그 대가로 `config.json`이 자격증명 없는 순수 설정 파일이 되고, 파일 유출 시의 피해 범위가 "누가 어떤 채널을 번역하는지" 수준으로 줄어든다.

**배제한 대안**: **id+토큰 영구 저장**(계획서 원안) — 재시작 후 API 호출이 없다는 이점이 있으나, 채널당 1회 호출은 무시할 만한 비용이고 자격증명을 디스크에 두는 대가가 그보다 크다.

### 2.2 `webhookCache` 필드와 타입을 삭제한다

**결정**: `GuildConfig.webhookCache`와 `WebhookCacheEntry` 타입을 제거한다. `configService`의 관련 정규화 코드도 함께 지운다.

**근거**: Phase 2에서 자리만 잡아두고 아무도 쓰지 않던 필드이며, 2.1에 따라 앞으로도 쓰지 않는 것이 확정되었다. 남겨두면 다음 작업자가 "왜 항상 비어 있는가"를 조사하게 되고, 언젠가 누군가 "미완성이니 채우자"고 판단할 여지가 생긴다.

**연쇄 효과**: `config.json`에서 자격증명이 사라지므로, 사양서 §4.2.1·개발 계획서 §4·CLAUDE.md에 적힌 "Webhook 토큰이 담기므로 `chmod 600`" 경고가 사실과 어긋나게 된다. 파일 권한 `0o600` 자체는 유지하되(서버별 채널·언어 설정도 공개할 정보는 아니다) 문구를 실제 위험 수준에 맞게 낮춘다.

### 2.3 Webhook 소실은 캐시 무효화로 자가 치유한다

**결정**: Webhook 전송이 실패하면 해당 채널의 캐시 항목을 Map에서 제거하고 그 메시지는 포기한다. 다음 메시지가 자연히 재조회·재생성한다.

**근거**: 관리자가 디스코드에서 Webhook을 삭제하면 전송이 `Unknown Webhook`(10015)으로 실패한다. 이때 즉시 재생성·재시도하는 로직을 넣을 수도 있으나, 캐시만 비워도 다음 메시지가 같은 결과를 만든다. 재시도 경로를 따로 두지 않는 편이 코드가 단순하고, 실패가 연속될 때 무한 재시도로 번지지 않는다.

### 2.4 첨부파일은 링크로 전달한다

**결정**: 원문의 첨부 URL을 본문 뒤에 텍스트로 덧붙인다. 파일을 내려받아 다시 올리지 않는다.

**근거**: 재업로드는 봇이 파일을 받아 다시 전송하므로 파일 크기만큼 egress를 소모한다. 이 프로젝트는 GCP e2-micro의 **월 1GB egress** 안에서 운영된다(사양서 §5). 영상 하나가 25MB라면 한 건에 월 예산의 2.5%가 나간다.

**알려진 한계**: Discord CDN 링크에는 서명 파라미터(`?ex=&is=&hm=`)가 붙어 만료될 수 있다. 시간이 지난 뒤 미러 채널을 스크롤하면 이미지가 깨져 보일 수 있다. egress 제약과 맞바꾼 결과이며, 향후 egress 여유가 생기거나 유료 호스팅으로 옮기면 재업로드로 전환을 검토한다.

**배제한 대안**:
- **무조건 재업로드**: 영구 보존되지만 위 egress 문제가 그대로다.
- **크기 상한을 두고 선택적 재업로드**: 절충안이지만 두 경로를 모두 유지해야 하고, 상한값을 정할 근거가 지금은 없다.

### 2.5 본문 없이 첨부만 있는 메시지도 전달한다

**결정**: 본문이 비어 있고 첨부가 있으면 **번역 API를 호출하지 않고** 첨부 링크와 원문 링크만 원 발신자 명의로 게시한다.

**근거**: Phase 3은 이런 메시지를 건너뛴다. 공지·모집 채널에서는 이미지 한 장이 본문 역할을 하는 경우가 흔하므로, 미러 채널만 보는 사람은 게시물이 올라온 사실 자체를 모르게 된다.

번역할 텍스트가 없으므로 API를 부르지 않는다 — 쿼터도 쓰지 않는다.

### 2.6 실패 알림은 봇 명의를 유지한다

**결정**: 번역 전부 실패 알림은 Webhook이 아니라 기존처럼 봇 메시지로 게시한다.

**근거**: 시스템 공지를 특정 사용자 이름과 아바타로 띄우면 그 사람이 그렇게 발언한 것처럼 보인다. 알림의 발신 주체는 봇이 맞다.

### 2.7 Webhook을 얻지 못하면 봇 명의로 폴백한다

**결정**: `fetchWebhooks`/`createWebhook`가 실패하면(등록 이후 `Manage Webhooks` 권한이 회수된 경우 등) 로그를 남기고 **봇 명의 게시로 폴백**한다. 이때는 작성자 이름을 본문 첫 줄에 굵게 넣는 Phase 3 형식을 쓴다.

**근거**: 이름이 덜 예쁘더라도 미러가 계속 도는 편이 조용히 멈추는 것보다 낫다. 이 프로젝트가 일관되게 택해온 방향이며(사양서 §4.2.2의 등록 시 권한 검증, §4.6의 failover), 등록 시점 검증은 이후의 권한 변경까지 막지 못한다.

### 2.8 사용자 이름은 Webhook 제약에 맞게 정제한다

**결정**: 서버 별명(`member.displayName`)을 우선 사용하되 Discord Webhook `username` 제약에 맞게 다듬는다. 1~80자, `discord`/`clyde` 포함 불가, `everyone`/`here` 불가. 정제 결과가 비면 계정명, 그것도 비면 `Unknown`으로 폴백한다.

**근거**: 제약을 어기면 전송이 400으로 실패한다. 사용자가 정한 별명을 봇이 통제할 수 없으므로 방어가 필요하다.

## 3. 아키텍처

### 3.1 파일 구조

```
src/
├── services/
│   ├── webhookService.ts      [신규] 채널별 Webhook 확보 + 메모리 캐시 + 무효화
│   └── webhookIdentity.ts     [신규] 사용자 이름 정제
├── events/
│   └── messageCreate.ts       [수정] postTranslation을 Webhook 전송으로 교체, 첨부 처리
├── services/configService.ts  [수정] webhookCache 정규화 제거
└── types/index.ts             [수정] WebhookCacheEntry 삭제, GuildConfig에서 webhookCache 제거
```

Phase 3 설계서 §2.7이 예고한 대로 `postTranslation` 한 곳만 바뀐다. 번역 로직(`translationService`, 제공자들), 큐, 분할 유틸은 그대로다.

### 3.2 최소 인터페이스로 테스트 가능하게

`webhookService`는 discord.js `TextChannel` 전체가 아니라 필요한 것만 요구한다.

```typescript
interface WebhookHost {
  id: string;
  fetchWebhooks(): Promise<Map<string, WebhookLike> | { find(fn: (w: WebhookLike) => boolean): WebhookLike | undefined }>;
  createWebhook(options: { name: string }): Promise<WebhookLike>;
}

interface WebhookLike {
  id: string;
  owner: { id: string } | null;
  send(options: WebhookSendOptions): Promise<unknown>;
}
```

`channelPermissions`가 채널 대신 이미 계산된 권한 객체를 받는 것과 같은 원칙이다 — discord.js 타입 의존을 줄이면 fake 객체 몇 줄로 단위 테스트가 된다.

실제 `TextChannel.fetchWebhooks()`는 `Collection`을 돌려주며 `Collection`은 `find`를 가지므로 구조적으로 호환된다.

## 4. 처리 흐름

1. `messageCreate` 수신 → 봇·Webhook 필터, 설정 조회 (Phase 3과 동일)
2. **본문이 비어 있고 첨부도 없으면** 종료
3. 채널별 큐에 투입 (Phase 3과 동일)
4. 출력 채널 확인 (Phase 3에서 번역 앞으로 옮겨둔 순서 유지)
5. **본문이 있으면** 번역 → 감지 언어가 타겟과 같으면 원문 사용. **본문이 없으면** 번역 생략
6. 게시할 본문 = 번역문(또는 원문) + 첨부 URL 목록
7. `webhookService`로 Webhook 확보
   - 성공 → 원 발신자 이름·아바타로 전송
   - 실패 → 로그 후 봇 명의 폴백(작성자 이름을 본문 첫 줄에 굵게)
8. 2000자 초과 시 분할, 원문 링크는 마지막 조각에만 (Phase 3의 `splitForDiscord` 재사용)

---

## 5. 에러 처리

| 상황 | 처리 |
|---|---|
| `fetchWebhooks`/`createWebhook` 실패 | 로그 후 봇 명의로 폴백 게시(§2.7) |
| Webhook 전송 실패 | 캐시에서 해당 채널 제거, 그 메시지는 포기, 로그. 다음 메시지가 재생성(§2.3) |
| 사용자 이름이 제약 위반 | 전송 전에 정제(§2.8). 정제 후에도 실패하면 위의 전송 실패 경로 |
| 첨부가 있으나 본문도 있음 | 정상 경로. 첨부 URL을 본문 뒤에 덧붙여 분할 대상에 포함 |
| 번역 전부 실패 | Phase 3과 동일 — 봇 명의 알림 + 채널당 10분 쿨다운 |

## 6. 테스트 전략

| 대상 | 방식 | 근거 |
|---|---|---|
| `webhookService` | 단위 테스트 | fake 채널로 캐시 히트, 소유자 판별(남의 Webhook을 쓰지 않는지), 없을 때 생성, 전송 실패 시 캐시 무효화를 검증 |
| `webhookIdentity` | 단위 테스트 | 80자 초과 절단, 금지어 처리, 빈 문자열 폴백 체인 |
| `messageCreate` 조립 | 단위 테스트 없음 | Phase 2·3과 동일 방침. discord.js `Message` 목킹 비용이 크고 판단 로직은 서비스에 있다 |

### 수동 검증 시나리오

1. 원본 채널에 메시지 → 출력 채널에 **원 발신자 이름과 아바타**로 게시
2. 서버 별명을 바꾸고 다시 전송 → 바뀐 별명으로 게시
3. 이미지만 첨부하고 본문 없이 전송 → 원 발신자 명의로 첨부 링크 게시
4. 본문 + 이미지 → 번역문과 첨부 링크가 함께
5. 디스코드에서 봇이 만든 Webhook을 삭제하고 다시 전송 → 자동 재생성되어 정상 게시
6. 봇 재시작 후 전송 → 정상 게시(메모리 캐시가 비어도 재조회됨)
7. 출력 채널에서 봇의 `Manage Webhooks` 권한을 제거하고 전송 → 봇 명의로 폴백 게시
8. 번역 전부 실패 상황 → 실패 알림이 **봇 명의**로 게시
