## 1. 배경과 범위

Phase 1에서 `/setting register|list|remove`의 **구조**(이름·서브커맨드·옵션·권한 게이트)를 정의하고 디스코드에 등록했다. 그러나 처리 로직이 없어 커맨드를 실행해도 응답이 없다.

Phase 2는 이 세 서브커맨드가 실제로 동작하게 만든다. 구체적으로 인터랙션 라우팅, 설정 CRUD, 메모리 캐시, 그리고 등록 시 유효성 검증을 구현한다.

**범위 밖**: 메시지 감지와 번역(Phase 3), Webhook 게시(Phase 4). 이 단계의 결과물은 "관리자가 설정을 등록·조회·삭제할 수 있고, 봇 재시작 후에도 유지된다"까지다.

## 2. 설계 결정

### 2.1 원본 채널당 설정은 1개

**결정**: 하나의 원본 채널은 최대 하나의 설정에만 등록될 수 있다. 이미 등록된 원본 채널을 다시 등록하려 하면 기존 설정을 덮어쓴다(2.2 참고).

**근거**: 사양서 §7은 "다중 타겟 언어 동시 번역"을 향후 확장 아이디어로 분류했다. 원본 채널 중복 등록을 허용하면 메시지 1건이 여러 번 번역되어 이 기능이 사실상 구현되는데, 이는 번역 API 호출량이 설정 개수에 비례해 늘어난다는 뜻이다. DeepL·Papago 무료 쿼터가 제한적인 상황에서 관리자가 의도치 않게 쿼터를 배로 소모하는 구조는 위험하다.

또한 이 제약 덕분에 Phase 3의 메시지 라우팅이 단순해진다. `messageCreate`에서 채널 ID로 설정을 조회할 때 결과가 0개 아니면 1개로 확정되므로, 반복 처리나 부분 실패 처리가 필요 없다.

**배제한 대안**:
- **허용**: 다국어 동시 번역이 공짜로 딸려오지만 쿼터 소모가 예측 불가능해진다. 향후 이 기능을 정식으로 도입할 때는 쿼터 관리와 함께 설계해야 한다.
- **허용하되 경고**: 경고는 읽히지 않는다. 제약을 걸 거면 명확히 걸고, 풀 거면 제대로 설계하는 편이 낫다.

### 2.2 재등록은 거부가 아니라 덮어쓰기

**결정**: 이미 등록된 원본 채널로 `/setting register`를 실행하면 기존 설정을 새 값으로 교체하고, 무엇이 어떻게 바뀌었는지 응답에 명시한다.

```
Updated the setting for #english-chat.
  Before: #korean-translation (한국어)
  After: #japanese-translation (日本語)
```

**근거**: 타겟 언어나 출력 채널을 바꾸는 것은 흔한 작업이다. 이를 "remove 후 register" 2단계로 강제하면, 중간에 설정이 사라진 상태가 생기고 조작 실수 여지도 커진다.

**배제한 대안**: **거부하고 remove를 안내** — 의도치 않은 덮어쓰기를 원천 차단하지만, 변경 내용을 명시적으로 보여주면 실수는 즉시 인지된다. 안전성 이득보다 번거로움이 크다.

### 2.3 `/setting remove`는 id + 자동완성

**결정**: `id` 옵션에 자동완성(autocomplete)을 붙인다. 표시는 `#원본 → #출력 (언어)`, 실제 값은 내부 ID다.

**근거**: 자동완성 목록을 봇이 직접 구성하므로 **원본 채널이 삭제된 고아 설정도 목록에 노출되어 삭제할 수 있다.**

**배제한 대안**:
- **`source-channel` 채널 피커**: 2.1에 따라 원본 채널이 고유 키가 되므로 자연스러워 보이지만, 디스코드 채널 피커는 **현재 존재하는 채널만** 보여준다. 채널이 삭제되면 그 설정을 영영 지울 수 없게 된다.
- **id 직접 입력**: `/setting list`로 조회 후 복사·입력하는 2단계가 매번 필요하다.

### 2.4 등록 시 봇 권한을 검증하고 부족하면 거부

**결정**: `/setting register` 처리 중 봇이 해당 채널들에서 실제로 동작할 수 있는지 확인하고, 부족하면 **무엇이 부족한지 채널별로 명시**해 거부한다.

| 채널 | 필요 권한 | 용도 |
|---|---|---|
| 원본 | `View Channel` | 메시지 이벤트 수신 (Phase 3) |
| 출력 | `View Channel`, `Send Messages`, `Manage Webhooks` | Webhook 생성 및 번역문 게시 (Phase 4) |

**근거**: 검증이 없으면 등록은 성공하지만 Phase 4에서 **조용히 실패**한다. 봇이 아무 반응 없이 가만히 있고, 원인을 알려면 VM에 접속해 로그를 봐야 한다. 설정 시점에 즉시 알려주는 편이 훨씬 낫다.

이는 CLAUDE.md의 "권한 검증 로직은 최소화" 결정과 충돌하지 않는다. 그 결정은 **사용자가 커맨드를 실행할 자격**을 봇이 판단하지 않는다는 뜻이며(그건 디스코드 명령어 권한에 위임), 여기서 확인하는 것은 **봇 자신이 그 채널에서 동작 가능한지**다. 서로 다른 문제다.

**배제한 대안**: **경고만 하고 등록 허용** — 경고를 무시하면 결국 조용한 실패로 돌아간다. **검사 안 함** — 가장 흔한 설정 실수를 가장 나쁜 방식으로 드러낸다.

### 2.5 응답은 ephemeral 평문

**결정**: 모든 `/setting` 응답은 ephemeral(호출자에게만 보임)이며, 임베드 없이 평문으로 구성한다.

**근거**: 설정 작업 결과가 채널에 남을 이유가 없다. 임베드는 시각적으로 낫지만 페이로드가 커지는데, e2-micro는 월 egress 1GB 제한이 있고 이 응답은 관리자만 본다.

### 2.6 설정 ID는 랜덤 단문자열

**결정**: `cfg_` + base36 6자 랜덤 (예: `cfg_k3f9a2`). 길드 내 충돌 시 재생성한다.

**근거**: 2.3의 자동완성 덕분에 사람이 ID를 읽거나 입력할 일이 없다. 순번(`cfg_01`)을 쓰면 카운터 상태를 유지해야 하고, 삭제 후 번호 재사용 여부라는 불필요한 결정이 따라온다.

### 2.7 config.json 경로는 `__dirname` 기준 상수

**결정**: `src/store/configPath.ts`에 `path.join(__dirname, 'config.json')`으로 정의하고, 이 상수를 유일한 출처로 삼는다.

**근거**: 상대 경로나 `process.cwd()` 기준으로 잡으면 pm2가 어느 디렉토리에서 실행하느냐에 따라 설정 파일 위치가 달라진다. 배포 후 "설정이 사라졌다"는 형태로 드러나는, 진단하기 나쁜 버그다.

위치를 `src/store/` 안에 두는 것은 개발 계획서 §3의 구조와 `.gitignore`에 이미 반영된 내용을 그대로 따른 것이다.

## 3. 아키텍처

### 3.1 파일 구조

```
src/
├── store/
│   ├── configPath.ts          [신규] config.json 정식 경로 상수
│   ├── jsonStore.ts           (변경 없음)
│   └── config.json            (런타임 생성, gitignore)
├── services/
│   ├── configService.ts       [신규] 메모리 캐시 + 설정 CRUD
│   └── channelPermissions.ts  [신규] 봇 권한 검사
├── commands/
│   └── setting.ts             [수정] 빌더에 execute·autocomplete 추가
├── events/
│   └── interactionCreate.ts   [신규] 인터랙션 라우팅
└── index.ts                   [수정] 초기화 + 이벤트 등록
```

### 3.2 책임 분리 원칙

**검증할 가치가 있는 로직은 services에, discord.js 의존은 commands에 둔다.**

`configService`는 discord.js를 전혀 import하지 않는다. 순수 데이터 조작이므로 Phase 1의 `jsonStore`와 같은 방식으로 임시 파일 기반 단위 테스트가 가능하다.

`channelPermissions`는 권한 비트 계산만 담당하며, 채널 객체에서 필요한 최소 인터페이스만 받는다. 따라서 작은 fake 객체로 테스트할 수 있다.

`setting.ts`의 핸들러는 인터랙션에서 옵션을 읽어 서비스에 넘기고 응답 문자열을 만드는 얇은 층으로 유지한다.

## 4. configService

### 4.1 인터페이스

```typescript
initialize(): void
listTranslations(guildId: string): TranslationConfig[]
findBySourceChannel(guildId: string, sourceChannelId: string): TranslationConfig | undefined
upsertTranslation(guildId: string, input: TranslationInput): UpsertResult
removeTranslation(guildId: string, id: string): TranslationConfig | undefined

interface TranslationInput {
  sourceChannelId: string;
  targetChannelId: string;
  targetLanguage: string;
}

interface UpsertResult {
  setting: TranslationConfig;
  replaced?: TranslationConfig;  // 덮어쓴 경우에만 존재
}
```

`initialize()`는 구동 시 1회 호출한다. import 시점이 아니라 명시적 호출로 두는 이유는, `deploy-commands.ts`가 `setting.ts`를 import할 때 설정 파일을 건드리지 않게 하기 위함이다.

### 4.2 로드 시 정규화 — Phase 1 이월 이슈 해결

Phase 1 최종 리뷰에서 `isValidStoreData`가 얕다는 지적이 있었다. `{version: 1, guilds: []}` 나 `translations` 필드가 없는 길드 항목이 검증을 통과하므로, Phase 2에서 `guild.translations.push(...)`를 호출하면 `undefined`에 대한 `TypeError`가 발생한다.

`initialize()`에서 로드 직후 정규화해 이를 막는다:

- `guilds`가 객체가 아니면 빈 객체로 대체
- 각 길드에 `translations` 배열이 없으면 빈 배열로 채움
- 각 길드에 `webhookCache` 객체가 없으면 빈 객체로 채움

정규화는 메모리 캐시에만 적용하며, 파일은 다음 쓰기 시점에 자연스럽게 갱신된다.

### 4.3 캐시와 디스크의 일관성

캐시를 먼저 수정하고 저장하면, 저장이 실패했을 때(디스크 가득참, 권한 오류 등) 메모리와 디스크가 어긋난 채 봇이 계속 동작한다. 다음 재시작에서 관리자가 방금 등록한 설정이 사라진다.

따라서 **사본 수정 → 저장 → 성공 시에만 캐시 반영** 순서를 따른다.

```
1. 현재 캐시를 깊은 복사
2. 복사본에 변경 적용
3. saveStore(CONFIG_PATH, 복사본)   ← 실패하면 여기서 throw
4. 캐시 = 복사본
```

저장이 실패하면 캐시는 손대지 않은 채 예외가 전파되고, 커맨드 핸들러가 사용자에게 실패를 알린다.

봇은 pm2 단일 프로세스로 운영하므로 프로세스 간 캐시 동기화는 고려하지 않는다.

## 5. 커맨드 동작

### 5.1 `/setting register`

순서대로 검사하며, 하나라도 걸리면 그 자리에서 거부한다.

1. **원본 == 출력 채널**: 거부. 번역문이 원본 채널로 되돌아가는 구성으로, 봇·Webhook 메시지를 무시하므로 무한 루프는 발생하지 않지만 명백한 설정 실수다.
2. **봇 권한 검사** (§2.4): 부족하면 채널별로 부족한 권한을 나열해 거부.
3. **기존 설정 확인**: 같은 원본 채널의 설정이 있으면 덮어쓰고 변경 내용을 안내(§2.2), 없으면 신규 등록.

### 5.2 `/setting list`

등록된 설정을 채널 멘션(`<#id>`) 형태로 나열한다. 설정이 없으면 그 사실과 함께 `/setting register` 사용을 안내한다.

원본 또는 출력 채널이 삭제된 경우 멘션이 깨진 형태로 표시되므로, 캐시된 채널 ID가 현재 길드에 존재하지 않으면 `(삭제된 채널)`로 표시해 정리 대상임을 드러낸다.

### 5.3 `/setting remove`

자동완성으로 선택된 ID의 설정을 삭제하고, 삭제된 내용을 응답한다. 해당 ID가 없으면(이미 삭제됐거나 잘못된 값) 그 사실을 알린다.

**자동완성 응답**: 현재 길드의 설정 목록을 캐시에서 읽어 `name`은 `#원본 → #출력 (언어)`, `value`는 설정 ID로 구성한다. 디스코드는 자동완성 선택지를 최대 25개까지 허용하므로 상한을 적용한다. 채널 멘션은 자동완성 목록에서 렌더링되지 않으므로 채널 이름을 직접 조회해 문자열로 넣는다.

## 6. 에러 처리

| 상황 | 처리 |
|---|---|
| 설정 저장 실패 | 캐시 롤백 없이 유지(§4.3), 사용자에게 실패 안내, 서버 로그에 원인 기록 |
| 알 수 없는 서브커맨드 | 일반 오류 응답. 커맨드 정의와 핸들러가 어긋난 상태이므로 로그에 남김 |
| 자동완성 처리 중 예외 | 빈 목록으로 응답. 자동완성 실패가 커맨드 전체를 막지 않게 한다 |
| 길드 밖(DM) 호출 | 길드 커맨드로 등록되어 실질적으로 발생하지 않으나, `interaction.guildId` 부재 시 방어적으로 거부 |
| `configService` 미초기화 | 구동 시 `initialize()` 실패는 프로세스를 중단시킨다. 설정을 읽을 수 없는 상태로 봇이 떠 있는 것보다 낫다 |

## 7. 테스트 전략

| 대상 | 방식 | 근거 |
|---|---|---|
| `configService` | 단위 테스트 | upsert 신규/덮어쓰기, 삭제, 정규화, ID 충돌 회피, 저장 실패 시 캐시 불변을 임시 경로로 검증 |
| `channelPermissions` | 단위 테스트 | 최소 fake 채널 객체로 부족 권한 목록의 정확성 검증 |
| `setting.ts` 핸들러 | 단위 테스트 없음 | discord.js `Interaction` 목킹 비용이 크고 검증 가치가 낮다. 판단 로직은 위 두 서비스로 추출했으므로 핸들러에 남는 것은 옵션 읽기와 문자열 조립뿐이다 |
| `interactionCreate` | 단위 테스트 없음 | 분기 2개(커맨드/자동완성)의 얇은 라우팅 |
| 커맨드 구조 | 기존 테스트 유지 | Phase 1의 5개 테스트가 계속 통과해야 한다 |

핸들러와 라우팅은 실제 디스코드에서 수동 검증한다. 구현 계획서에 다음 시나리오를 체크리스트로 포함한다:

1. 신규 등록 성공
2. 같은 원본 채널 재등록 → 변경 내용 안내와 함께 덮어쓰기
3. 원본 == 출력 채널 → 거부
4. 봇 권한이 없는 채널을 출력으로 지정 → 부족 권한 명시하며 거부
5. `list` 조회 → 등록 내용 표시
6. `remove` 자동완성 → 목록 표시 및 삭제
7. 봇 재시작 후 `list` → 설정 유지 확인
