## 1. 배경과 범위

Phase 2까지 관리자가 "원본 채널 → 출력 채널 → 타겟 언어"를 등록할 수 있게 되었지만, 등록된 설정을 실제로 쓰는 코드가 없다. 봇은 메시지를 듣지 않는다.

Phase 3은 그 설정을 살아 움직이게 만든다. 원본 채널의 메시지를 감지해 번역하고, 결과를 출력 채널에 게시한다.

**범위 밖**: Webhook을 통한 원 발신자 명의 게시와 첨부파일 전달(Phase 4), pm2 배포(Phase 5).

## 2. 설계 결정

### 2.1 번역 제공자를 Papago에서 Google Translate로 교체

**결정**: 지원 제공자를 **DeepL(1순위), Google Translate(2순위)** 로 변경한다. Papago는 제외한다.

**근거**: Papago는 더 이상 무료로 접근할 수 없다.

- 2024-02-29: `developers.naver.com`의 파파고 API 무료 제공이 종료되고 네이버 클라우드 플랫폼으로 이관(유료화)
- 2025-03-20: AI NAVER API 콘솔의 Papago 서비스도 종료. 현재는 NCP AI Service 콘솔에서만 이용 가능

이 프로젝트는 무료 티어 운영을 전제로 한다(사양서 §5의 호스팅 선택 기준과 동일한 이유). 유료 NCP 연동은 그 전제에 맞지 않는다.

**파급효과**: `target-language` 선택지 10개는 "DeepL ∩ Papago 공통 지원"을 근거로 골랐다. 그 근거는 무효가 되었으나 **목록 자체는 유지한다** — 10개 모두 DeepL이 지원하므로 1순위가 처리 가능하고, Google은 130개 이상을 지원하므로 2순위 보완에도 문제가 없다. 근거 문구만 "DeepL 지원 기준, Google이 2순위로 보완"으로 고쳐 쓴다. Google 도입으로 목록을 넓힐 수는 있지만 지금 필요하다는 근거가 없어 넓히지 않는다.

### 2.2 DeepL 엔드포인트는 API 키에서 자동 판별

**결정**: 키가 `:fx`로 끝나면 `https://api-free.deepl.com/v2/translate`, 아니면 `https://api.deepl.com/v2/translate`를 사용한다.

**근거**: DeepL은 무료 키와 유료 키의 호스트가 다르고, 무료 키에는 `:fx` 접미사가 붙는다. 이를 별도 환경변수(`DEEPL_API_HOST` 같은)로 두면 사용자가 키와 호스트를 어긋나게 설정할 수 있고, 그때 나오는 오류(403)는 원인을 짐작하기 어렵다. 키 자체에 정보가 들어 있으므로 코드가 판별하는 편이 틀릴 여지가 없다.

### 2.3 언어 감지는 번역 API에 맡긴다

**결정**: 로컬 언어 감지를 하지 않는다. 항상 번역 API를 호출하고, 응답에 포함된 감지 언어가 타겟과 같으면 **번역문 대신 원문**을 게시한다.

**근거**: 사양서 §4.1은 "타겟 언어와 동일하면 번역 API 호출을 생략"이라고 적었으나, 이는 호출 **전에** 언어를 알아야 성립한다. 디스코드 메시지는 짧고 노이즈가 많아(`ㅇㅇ`, `thanks`, 이모지 단독) 통계적 언어 감지의 정확도가 낮다.

오판의 결과가 비대칭적이라는 점이 결정적이다:

- **잘못 건너뜀** → 메시지가 출력 채널에 아예 올라오지 않는다. 사용자는 누락 사실조차 모른다.
- **불필요하게 번역함** → 쿼터를 조금 더 쓴다. 결과물은 정상이다.

전자가 훨씬 나쁘므로, 정확도를 사서 쿼터를 지불한다. 실제 손실도 작다 — 원본 채널이 타겟과 다른 언어로 운영되는 것이 정상 상태이므로, 동일 언어 메시지는 소수다.

**배제한 대안**:
- **`franc` 사전 감지**: 사양서 문구 그대로지만, 10자 미만 문장에서 오판이 잦아 짧은 채팅이 조용히 누락된다. 의존성도 추가된다.
- **스크립트 기반 휴리스틱**(한글/가나/한자/라틴 비율): CJK와 라틴 구분은 통계적 감지보다 확실하지만, 언어별 판별 코드를 직접 쓰고 유지해야 한다. 아끼는 쿼터에 비해 비용이 크다.

이에 따라 사양서 §4.1의 "번역 API 호출을 생략하고"는 "번역 API 응답의 감지 언어가 타겟과 같으면 번역문 대신 원문을 게시한다"로 수정한다.

### 2.4 실패는 종류를 가리지 않고 다음 제공자로 넘긴다

**결정**: 타임아웃, 네트워크 오류, 429, DeepL 456(쿼터 초과), 5xx, 인증 실패 등 **모든 실패를 동일하게 취급**해 다음 순위 제공자를 시도한다. 오류 코드별 재시도 가능 여부를 판정하지 않는다.

**근거**: 제공자마다 오류 코드 체계가 다르고, "이 오류는 다음 제공자에서도 실패할 것"이라는 판단은 틀릴 수 있다. 그 판단이 틀렸을 때 잃는 것(번역 누락)이 맞았을 때 아끼는 것(불필요한 호출 1회)보다 훨씬 크다.

제공자당 **10초 타임아웃**을 건다(`AbortSignal.timeout`). 타임아웃이 없으면 멈춘 요청 하나가 해당 채널 큐 전체를 무기한 막는다. 최악의 경우 두 제공자 합쳐 20초가 걸린다.

### 2.5 전부 실패하면 출력 채널에 알리되 쿨다운을 건다

**결정**: 모든 제공자가 실패하면 출력 채널에 알림을 게시한다. 단 **같은 채널에는 10분에 한 번만** 알린다. 쿨다운 상태는 메모리에만 두고 재시작 시 초기화한다.

**근거**: 조용한 실패와 도배 사이의 절충이다.

조용히 실패하면 출력 채널만 보는 사람들은 "원본 채널이 한산하구나"라고 오해한다. 번역 봇에 의존하는 사용자에게 이는 잘못된 정보다.

반대로 메시지마다 알리면, 쿼터 소진처럼 **연속 실패하는 장애**에서 출력 채널이 오류로 도배된다. 정작 필요한 정보(장애 발생 사실)는 첫 알림 하나로 충분하다.

**배제한 대안**:
- **원본 메시지에 ⚠️ 리액션**: 출력 채널이 깨끗하지만 원본 채널에 `Add Reactions` 권한이 추가로 필요해지고(등록 시 권한 검증도 수정해야 함), 정작 오해하게 되는 출력 채널 독자는 여전히 모른다.
- **로그만 기록**: 운영자가 VM 로그를 볼 때까지 아무도 모른다.

### 2.6 채널별 직렬 큐

**결정**: 같은 원본 채널의 메시지는 들어온 순서대로 하나씩 처리하고, 다른 채널끼리는 병렬로 처리한다.

**근거**: 쿼터나 레이트 리밋보다 **대화 순서**가 결정적이다. 병렬로 처리하면 긴 메시지(번역 느림)와 짧은 메시지(빠름)가 연달아 왔을 때 번역문이 뒤바뀐 순서로 게시된다. 200ms 간격으로 오는 대화에서 충분히 흔한 일이며, 그 결과 출력 채널의 대화는 읽을 수 없게 된다.

채널별 Promise 체인으로 구현하면 5줄 수준이고, 자연스러운 백프레셔도 얻는다.

**배제한 대안**:
- **전역 직렬 큐**: 순서 보장은 가장 확실하지만 한 채널이 바쁘면 다른 채널 번역이 전부 밀린다.
- **큐 없이 병렬**: 구현은 가장 작지만 위 순서 문제가 그대로 남는다.

### 2.7 Phase 3이 게시까지 담당하고, Phase 4에서 전송 계층만 교체

**결정**: Phase 3은 봇 명의의 평범한 메시지로 번역 결과를 출력 채널에 게시한다. Phase 4에서 Webhook 전송으로 교체해 원 발신자 이름·아바타를 입힌다.

**근거**: 각 Phase는 그 자체로 동작하고 검증 가능한 결과물을 내야 한다. Phase 3이 번역만 하고 게시하지 않으면 디스코드에서 확인할 방법이 없어 단위 테스트와 로그에만 의존하게 된다.

버려지는 코드는 전송 계층 한 곳뿐이다. Phase 4는 그 함수의 구현을 바꾸고 첨부파일 전달을 더한다.

## 3. 아키텍처

### 3.1 파일 구조

```
src/
├── services/
│   ├── providers/
│   │   ├── deepl.ts          [신규] DeepL 호출 + 자체 언어코드 매핑
│   │   └── google.ts         [신규] Google 호출 + 자체 언어코드 매핑
│   ├── translationService.ts [신규] 우선순위 failover + 타임아웃
│   └── messageQueue.ts       [신규] 채널별 직렬 실행
├── events/
│   └── messageCreate.ts      [신규] 필터 → 큐 → 번역 → 게시
└── index.ts                  [수정] 인텐트 추가 + 핸들러 등록
```

### 3.2 언어코드 매핑을 제공자 안에 두는 이유

봇 내부 코드는 `/setting`의 choices 값(`ko`, `en`, `ja`, `zh-CN`, `es`, `fr`, `de`, `ru`, `it`, `id`)이다. 제공자별로 표기가 다르다.

- **DeepL**: 대문자를 요구하고, 타겟 언어로 `EN`은 폐기되어 `EN-US`/`EN-GB` 중 하나를 써야 한다. 중국어 간체는 `ZH`.
- **Google**: 대체로 내부 코드와 같다. 중국어 간체는 `zh-CN` 그대로.

이 차이는 각 제공자의 사정이지 시스템 공용 지식이 아니다. 공용 매핑 모듈을 만들면 제공자를 추가할 때마다 그 파일을 고쳐야 하고, 어느 표기가 누구 것인지 흐려진다. 제공자가 자기 방언을 아는 편이 응집도가 높다.

### 3.3 제공자 인터페이스

```typescript
interface TranslationResult {
  text: string;
  detectedSourceLanguage: string;  // 봇 내부 코드로 정규화
}

interface TranslationProvider {
  name: string;
  translate(text: string, targetLanguage: string): Promise<TranslationResult>;
}
```

핵심은 **제공자가 감지 언어를 내부 코드로 되돌려 반환한다**는 점이다. DeepL은 `EN-US`를, Google은 `en`을 돌려주지만 둘 다 `en`으로 정규화된다. 덕분에 상위 계층은 어느 제공자가 응답했든 `detected === targetLanguage` 비교를 똑같이 할 수 있다.

`fetch`를 주입 가능하게 만들어(기본값은 전역 `fetch`) 단위 테스트가 네트워크에 나가지 않게 한다.

## 4. 처리 흐름

1. `messageCreate` 수신
2. **봇·Webhook 메시지면 즉시 종료** (`message.author.bot || message.webhookId`) — 사양서 §4.1의 루프 방지
3. `configService.findBySourceChannel(guildId, channelId)`로 설정 조회. 없으면 종료. 메모리 캐시만 참조하므로 파일 I/O가 없다
4. 본문(`message.content`)이 비어 있으면 종료 — 첨부만 있는 메시지는 Phase 4에서 다룬다
5. **채널별 큐에 투입**
6. `translationService.translate(text, targetLanguage)` — DeepL → 실패 시 Google → 둘 다 실패 시 예외
7. `detectedSourceLanguage === targetLanguage`이면 번역문 대신 **원문**을 게시 대상으로 삼는다
8. 출력 채널에 봇 명의로 게시. 2000자를 넘으면 분할하고 원문 링크는 마지막 조각에만 붙인다 (사양서 §4.4, §4.5)

## 5. 에러 처리

| 상황 | 처리 |
|---|---|
| 1순위 제공자 실패 | 사유를 로그에 남기고 2순위 시도 |
| 모든 제공자 실패 | 시도 내역을 담은 예외 → 핸들러가 출력 채널에 알림(채널당 10분 쿨다운) + 로그 |
| 출력 채널이 삭제됨 / 접근 불가 | 게시 실패를 로그에 남기고 그 메시지는 포기. 큐는 계속 진행 |
| 큐 작업 중 예외 | 큐 체인이 끊기지 않도록 각 작업을 개별적으로 감싼다. 한 메시지의 실패가 이후 메시지 처리를 막으면 안 된다 |
| 설정은 있으나 봇이 출력 채널 권한을 잃음 | 게시 실패로 처리(위와 동일). 등록 시점 검증(§4.2.2)은 이후 권한 변경까지 막지 못한다 |

## 6. 테스트 전략

| 대상 | 방식 | 근거 |
|---|---|---|
| `providers/deepl.ts`, `providers/google.ts` | 단위 테스트 | 주입한 가짜 `fetch`로 언어코드 매핑, 응답 파싱, 감지 언어 정규화, HTTP 오류의 예외 변환을 검증. 네트워크에 나가지 않는다 |
| `translationService.ts` | 단위 테스트 | 가짜 제공자로 failover 순서, 1순위 실패 시 2순위 사용, 전부 실패 시 예외, 타임아웃 동작 |
| `messageQueue.ts` | 단위 테스트 | 동시 투입 시 채널 내 순서 보장, 채널 간 병렬, 한 작업의 예외가 후속 작업을 막지 않음 |
| `events/messageCreate.ts` | 단위 테스트 없음 | discord.js `Message` 목킹 비용이 크고 실익이 낮다. 판단 로직은 위 세 모듈에 있고 여기 남는 것은 필터와 조립이다 |

Phase 2와 동일한 원칙이다 — 검증할 가치가 있는 로직을 discord.js에 의존하지 않는 모듈로 빼낸다.

### 수동 검증 시나리오

1. 원본 채널에 타겟과 다른 언어로 메시지 → 출력 채널에 번역문 + 원문 링크
2. 원본 채널에 타겟과 **같은** 언어로 메시지 → 출력 채널에 원문 그대로
3. 봇이 출력 채널에 올린 메시지가 다시 번역되지 않음 (루프 방지)
4. 짧은 메시지 여러 개를 빠르게 연속 전송 → 출력 채널에서 **순서가 유지됨**
5. 2000자를 넘는 긴 메시지 → 분할 게시, 마지막 조각에만 원문 링크
6. `.env`의 두 API 키를 모두 잘못된 값으로 바꾸고 재시작 → 출력 채널에 실패 알림 1회, 이후 10분간 재알림 없음
7. 첨부만 있고 본문이 없는 메시지 → 아무 일도 일어나지 않음 (Phase 3 범위 밖임을 확인)

## 7. Phase 3에서 하지 않는 것
