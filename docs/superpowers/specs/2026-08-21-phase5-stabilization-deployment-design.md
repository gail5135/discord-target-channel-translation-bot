## 1. 배경과 범위

Phase 4까지 기능은 완성되었다. 봇은 원본 채널을 감시해 번역하고, 원 발신자 명의로 출력 채널에 게시한다. 지금까지는 개발자 노트북에서 `npm start`로 돌려왔다.

Phase 5는 이것을 **24시간 도는 서버 프로세스로 넘긴다.** 새 기능은 없다. 대신 오래 돌 때만 드러나는 문제를 정리하고, 배포에 필요한 산출물과 절차를 만든다.

**범위 조정 — 실제 서버 구축은 이 단계에서 하지 않는다.** GCP e2-micro 인스턴스가 아직 없고, 인스턴스 생성과 SSH 접속은 사람이 직접 해야 한다. Phase 5는 **준비물과 절차 문서**를 완성하는 데까지다.

## 2. 설계 결정

### 2.1 로깅 라이브러리를 도입하지 않는다

**결정**: `console.log`/`console.error`를 그대로 쓴다. 타임스탬프는 pm2의 `time: true`가 붙인다.

**근거**: 로그 레벨을 실제로 쓰는 곳이 없다 — 기록할 가치가 있는 사건은 거의 전부 오류이고 이미 `console.error`다. `winston`이나 `pino`를 넣으면 의존성과 초기화 코드가 늘지만 얻는 것은 지금 안 쓰는 기능들이다. CLAUDE.md의 "무거운 의존성 추가를 피하라"에도 어긋난다.

**배제한 대안**: **구조화 로거 도입** — 로그를 기계로 수집·질의할 계획이 생기면 그때가 도입 시점이다. 지금은 `pm2 logs`로 사람이 읽는다.

### 2.2 로그에 남기지 않을 두 가지를 규칙으로 못박는다

**결정**: 아래 두 가지는 어떤 경우에도 로그에 넣지 않는다. CLAUDE.md와 이 문서에 규칙으로 남긴다.

1. **REST 오류 객체를 그대로 넘기지 않는다.** `@discordjs/rest`가 요청 URL을 통째로 담는데 Webhook 요청 URL에는 토큰이 들어 있다. Webhook 관련 오류는 `webhookService.describeError()`를 거친다.
2. **메시지 본문을 로그에 남기지 않는다.**

**근거**: 1번은 Phase 4 최종 리뷰에서 실제로 발견된 유출이다. 규칙으로 남기지 않으면 다음에 오류 처리를 추가하는 사람이 같은 실수를 반복한다.

2번은 아직 위반한 적이 없지만 유혹이 확실하게 온다. 번역이 이상하게 나왔다는 제보를 받으면 "원문이 뭐였는지 찍어보자"가 가장 먼저 떠오르는 대응이다. 그 순간부터 로그 파일은 사용자 대화 기록이 되고, 백업·전송·보관 정책이 전부 따라붙는다. 디버깅이 필요하면 메시지 ID와 채널 ID를 남긴다 — 원문은 디스코드에서 링크로 확인할 수 있다(사양서 §4.5).

### 2.3 로그 로테이션은 선택이 아니다

**결정**: `pm2-logrotate`를 설치하고 크기 상한과 보관 개수를 설정한다. 배포 절차의 필수 단계로 넣는다.

**근거**: pm2는 기본적으로 로그를 무한히 쌓는다. e2-micro의 디스크는 30GB이고, 로그가 채우면 죽는 것은 봇이 아니라 서버다 — 그 상태에서는 SSH 접속도 어려워진다. 번역 봇은 실패 시 메시지마다 로그를 남기므로(제공자 failover, 큐 실패) 장애가 길어지면 증가 속도가 빨라진다.

`pm2-logrotate`는 pm2 자체 모듈이라 `package.json`과 무관하다. "새 npm 패키지를 추가하지 않는다"는 제약에 걸리지 않는다.

### 2.4 크래시 루프를 차단한다

**결정**: `ecosystem.config.js`에 `max_restarts`와 `min_uptime`을 설정해, 짧은 시간에 반복 실패하면 pm2가 재시작을 포기하도록 한다.

**근거**: 봇은 `.env`가 없거나 API 키가 하나도 없으면 **기동 즉시** 종료된다(설계상 의도된 동작 — 번역할 수 없는 상태로 떠 있는 것보다 낫다). pm2 기본 설정은 이때 무한히 재시작을 시도하며 CPU를 태우고 로그를 채운다. 공유 vCPU 한 개인 e2-micro에서는 이것만으로도 서버가 반응하지 않게 된다.

`max_memory_restart`도 함께 둔다. 누수가 있어도 서버 전체를 끌어내리기 전에 프로세스만 재시작된다.

### 2.5 이월 백로그를 전부 정리한다

**결정**: 다섯 Phase에 걸쳐 쌓인 이월 항목을 이 단계에서 전부 닫는다. 아래가 그 전부이며, 목록에 없는 것은 남아 있지 않다.

**장기 실행에서 실제로 문제가 되는 3건:**

| 항목 | 문제 |
|---|---|
| 쿨다운 맵 증가 | `lastFailureNotice`·`lastUnavailableLog`에 항목이 추가되기만 하고 제거되지 않는다. 실패를 겪은 채널 수만큼 영구히 남는다 |
| 설정 삭제 후 웹훅 토큰 잔존 | `/setting remove`로 설정을 지워도 그 출력 채널의 웹훅이 메모리 캐시에 남는다. 토큰 보유 시간을 최소화한다는 §2.1(Phase 4)의 취지에 어긋난다 |
| `translations[]` 원소 미검증 | 로드 시 배열 여부만 확인하고 원소는 보지 않는다. 사양서 §4.2.1이 손편집을 장점으로 광고하므로 실제로 도달 가능한 경로이며, 필드가 빠진 원소는 핸들러에서 터진다 |

**정리 성격 — 안 해도 돌아가지만 읽는 사람을 헷갈리게 하는 것들:**

1. `createdAt`이 덮어쓰기 후 "최종 수정"을 의미한다 — 이름과 실제가 다르다
2. `setting.ts`의 길드 전용 거부 응답이 세 번, 저장 실패 응답이 두 번 중복
3. `channelLabel`과 `nameOf`가 같은 조회를 다른 형식으로 두 번 구현
4. `configService.requireCache()`의 미초기화 예외 경로에 테스트가 없다
5. `FROM_GOOGLE`의 `zh`·`zh-Hans` 별칭에 테스트가 없다
6. `createTranslator`의 비-`Error` throw 처리에 테스트가 없다
7. `initializeTranslator`/`translate` 배선에 테스트가 없다
8. `channel as unknown as WebhookHost`가 discord.js와의 유일한 미검사 이음매인데 주석이 없다

**근거**: 배포 직전이 이것을 닫을 마지막 자연스러운 시점이다. 서버에 올라간 뒤에는 같은 수정도 배포 절차를 한 번 더 거쳐야 하고, 운영 중 발견되는 문제와 섞이면 원인 분리가 어려워진다.

### 2.6 통합 테스트를 "테스트 서버 → 실 서버"에서 "배포 후 재검증"으로 바꾼다

**결정**: 개발 계획서 §6이 적은 "테스트 서버에서 통합 테스트 후 실 서버 적용" 대신, **배포한 서버 환경에서 Phase 1~4의 수동 시나리오를 다시 한 번** 돌린다.

**근거**: 디스코드 서버가 하나뿐이라 "테스트 서버 → 실 서버" 구분이 성립하지 않는다. 그리고 진짜 확인할 것은 기능이 아니다 — 기능은 이미 로컬에서 검증했다. **로컬에서 통과한 것이 e2-micro에서도 통과하는가**가 확인 대상이며, 그것은 배포한 뒤에만 알 수 있다.

### 2.7 모니터링·CI/CD·컨테이너를 넣지 않는다

**결정**: 외부 모니터링, 알림 연동, CI/CD 파이프라인, Docker를 도입하지 않는다.

**근거**:
- **모니터링·알림**: 쿼터 소진 같은 실사용 장애는 이미 출력 채널에 알린다(사양서 §4.6). 그 이상은 무료 티어에 얹을 것이 마땅치 않고, 지금 필요하다는 근거가 없다.
- **CI/CD**: 이전에 "배포하고 나서 생각"으로 미뤄둔 항목이다. 배포가 `git pull` + `npm ci` + `pm2 restart` 세 줄이라 자동화가 아끼는 것이 적다.
- **Docker**: RAM 1GB에서 런타임 오버헤드만 늘어난다. 단일 Node 프로세스에 격리 이득도 없다.

### 3.1 `docs/deployment.md`가 담을 것

1. GCP e2-micro 인스턴스 생성 (리전 제약: `us-west1`/`us-central1`/`us-east1`)
2. Node.js 22 설치
3. GitHub 공개 저장소에서 `git clone`
4. `npm ci`
5. `.env` 작성과 `chmod 600` — 저장소에 없으므로 서버에서 직접 만든다
6. `npm run deploy-commands` 1회 실행 (슬래시 커맨드 등록)
7. `pm2 start ecosystem.config.js`
8. `pm2 install pm2-logrotate` + 설정
9. `pm2 startup` + `pm2 save` (부팅 시 자동 시작)
10. 갱신 절차: `git pull` → `npm ci` → `pm2 restart` (커맨드 정의가 바뀐 경우에만 `deploy-commands` 재실행)
11. 롤백 절차: `git checkout <이전 커밋>` → `npm ci` → `pm2 restart`
12. 배포 체크리스트 — 인텐트 활성화, 봇 권한, `.env` 권한, 로그 로테이션 동작 확인

### 3.2 공개 저장소 안전성

푸시 전 확인을 마쳤다. `.env`와 `src/store/config.json`은 **전체 히스토리에서 한 번도 커밋된 적이 없고**, 커밋 diff 전체에서 토큰 형태 문자열이 검색되지 않으며, 추적 파일에 실제 Discord ID가 없다(문서의 ID는 전부 `111111111111111111` 같은 더미). 지금 상태로 공개해도 안전하다.

`README.md`에 이 사실을 근거로 "`.env`는 저장소에 없으니 서버에서 직접 만들라"는 안내를 넣는다.

## 4. 에러 처리

이 단계에서 새로 정의하는 것은 프로세스 수준의 동작이다. 애플리케이션 내부의 실패 처리는 Phase 3·4에서 이미 정의했다.

| 상황 | 처리 |
|---|---|
| `.env` 누락·API 키 없음 | 기동 즉시 종료(기존 동작). pm2가 `max_restarts` 안에서 재시도하다 포기 |
| 메모리 누수 | `max_memory_restart` 도달 시 프로세스만 재시작 |
| 정상 크래시 | pm2가 재시작 |
| 로그 증가 | `pm2-logrotate`가 크기·보관 개수로 제한 |
| 서버 재부팅 | `pm2 startup`으로 등록된 systemd 유닛이 자동 기동 |

## 5. 테스트 전략

| 대상 | 방식 |
|---|---|
| 백로그 정리 중 로직 변경분 | 단위 테스트 — 쿨다운 맵 정리, 설정 삭제 시 웹훅 캐시 제거, `translations[]` 원소 정규화 |
| 백로그의 테스트 공백 4건 | 해당 경로에 테스트 추가 |
| `ecosystem.config.js` | 단위 테스트 없음 — pm2가 읽는 설정 파일이며 검증은 실제 배포에서 이루어진다 |
| 문서 | 검증 대상 아님 |

### 수동 검증 시나리오

배포 후 서버에서 확인한다.

1. `pm2 start` 후 `pm2 logs`에 `[translation] providers: deepl -> google`과 로그인 로그
2. 원본 채널에 메시지 → 출력 채널에 원 발신자 명의로 게시 (Phase 4 시나리오 1 재확인)
3. `pm2 restart` 후 다시 전송 → 정상 게시, 웹훅 개수 불변
4. 서버 재부팅 → 봇이 자동 기동
5. `.env`의 `DISCORD_TOKEN`을 일부러 망가뜨리고 `pm2 restart` → 무한 재시작 없이 pm2가 포기(`pm2 status`가 `errored`). 복구 후 정상 기동
6. `pm2 logs`에 메시지 본문이 남지 않는지 확인
7. `ls -l .env`로 권한이 `600`인지 확인
8. `/setting remove` 후 같은 출력 채널로 다시 `/setting register` → 정상 게시(Webhook 캐시 무효화 경로. 단위 테스트가 없는 유일한 백로그 수정이다)
