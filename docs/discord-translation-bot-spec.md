## 1. 개요

본 문서는 다국어 사용자가 함께 활동하는 디스코드 서버에서, 지정된 채널의 대화를 상시 모니터링하여 타겟 언어로 자동 번역한 뒤, 이를 별도로 지정된 채널에 게시하는 디스코드 봇의 기획 배경과 핵심 기능을 정의한다.

---

## 2. 기획 배경

### 2.1 문제 정의
- 다국적 멤버가 함께 활동하는 디스코드 서버(커뮤니티, 팀 협업 서버 등)에서는 언어 차이로 인한 소통 장벽이 발생한다.
- 사용자가 매번 메시지를 복사해 번역기를 따로 사용하는 것은 번거롭고, 대화의 실시간성을 해친다.
- 기존 번역 봇들은 번역 메시지가 봇 명의로 표시되어 누가 원래 발언한 내용인지 파악하기 어렵거나, 원문 확인이 불편한 경우가 많다.

### 2.2 기대 효과
- 실시간 대화 흐름을 유지하면서 언어 장벽 없이 소통 가능
- 번역 메시지에서도 원 발신자를 명확히 인지할 수 있어 대화 맥락 유지
- 원문 확인이 필요할 때 바로 이동 가능하여 신뢰성 있는 번역 경험 제공

---

## 3. 목표 및 대상

### 3.1 목표
- 서버/채널 단위로 설정된 타겟 언어로 메시지를 자동 번역하여 제공
- 번역 메시지의 가독성과 발신자 신뢰성을 최대한 원본 메시지에 가깝게 유지

### 3.2 대상
- 다국어 멤버가 혼재된 커뮤니티 서버
- 해외 팀원과 협업하는 프로젝트/업무용 서버

---

## 4. 핵심 기능 명세

### 4.1 자동 번역
- 봇은 사전에 지정된 **모니터링 대상 채널(원본 채널)**을 항상 감시하며, 해당 채널에 새 메시지가 입력될 때마다 이를 감지한다.
- 감지된 메시지는 자동으로 타겟 언어로 번역되며, 번역된 결과는 원본 채널이 아닌 **별도로 지정된 출력 채널(번역 채널)**에 새 메시지로 작성된다.
- 즉, 원본 채널의 대화 내용이 실시간으로 번역되어 다른 채널에 스트리밍되듯 게시되는 방식이다.
- 원문 언어 감지는 자동으로 수행되며, 타겟 언어와 동일한 언어로 작성된 메시지는 번역 API 호출을 생략하고 원문 그대로 출력 채널에 게시한다(원문 링크는 동일하게 포함).
- 모니터링 대상 채널과 출력 채널은 1:1 또는 N:1(여러 원본 채널 → 하나의 출력 채널) 구조로 설정 가능하도록 확장성을 고려한다.
- 봇 또는 Webhook이 작성한 메시지(`author.bot` 또는 `webhookId` 존재)는 모니터링 대상에서 무조건 제외한다. 출력 채널이 다른 설정의 원본 채널로 잡히는 등의 경우에 번역 루프가 발생하는 것을 막기 위함이며, 별도의 채널 중복 등록 검증 로직은 두지 않는다.
- 원본 메시지가 게시 이후 수정되거나 삭제되어도 이미 게시된 번역 메시지는 그대로 둔다(v1 범위 밖). 최신 원문 확인은 4.5의 원문 링크로 대응한다.

### 4.2 타겟 언어 설정
- 서버 관리자(또는 지정된 권한을 가진 사용자)가 **슬래시 커맨드**를 통해 모니터링 채널, 출력 채널, 타겟 언어를 설정할 수 있다.
- 설정은 "모니터링 채널 - 출력 채널 - 타겟 언어"가 하나의 세트로 등록되는 구조로 한다.
- 예시 명령어: `/setting register source-channel:#영어대화 target-channel:#한글번역 target-language:한국어`
- 설정 방식으로 서버 `.env` 대신 슬래시 커맨드를 채택한 이유:
  - 서버(길드)마다 다른 채널/언어 값을 가져야 하므로, 배포 시점에 고정되는 env 방식은 서버별 개별 설정이 불가능하거나 매우 번거로움
  - 슬래시 커맨드는 관리자가 봇 재시작 없이 즉시 설정을 등록/수정/조회할 수 있어 운영 편의성이 높음
  - 여러 서버에 봇이 동시 설치되는 구조(멀티 테넌트)를 고려할 때 서버별 독립 설정이 필수적
- 단, 슬래시 커맨드는 입력 인터페이스 역할만 하며, 등록된 설정 값 자체는 별도 저장소에 영구 저장(persist)하여 봇 재시작 후에도 유지되도록 한다.

#### 4.2.2 등록 규칙

상세 근거는 `docs/superpowers/specs/2026-08-07-phase2-setting-commands-design.md` 참고.

- **원본 채널당 설정은 1개로 제한한다.** 같은 원본 채널을 여러 출력 채널·언어로 중복 등록하면 메시지 1건이 여러 번 번역되어 번역 API 쿼터가 설정 개수에 비례해 소모된다. 7장의 "다중 타겟 언어 동시 번역"은 쿼터 관리와 함께 별도로 설계한다.
- **이미 등록된 원본 채널을 다시 등록하면 기존 설정을 덮어쓴다.** 무엇이 어떻게 바뀌었는지(이전 출력 채널·언어 → 새 값) 응답에 명시한다. 타겟 언어 변경을 "삭제 후 재등록" 2단계로 강제하지 않기 위함이다.
- **원본 채널과 출력 채널이 같으면 거부한다.** 봇·Webhook 메시지는 무시하므로 무한 루프는 발생하지 않지만 명백한 설정 실수다.
- **등록 시 봇이 해당 채널에서 동작 가능한지 검증하고, 부족하면 무엇이 부족한지 명시해 거부한다.** 원본 채널에는 `View Channel`, 출력 채널에는 `View Channel`·`Send Messages`·`Manage Webhooks`가 필요하다. 검증이 없으면 등록은 성공하고 실제 게시 단계에서 조용히 실패하므로, 원인을 찾으려면 서버 로그를 봐야 한다.
  - 이는 6.1의 "권한 검증 최소화" 원칙과 충돌하지 않는다. 그 원칙은 **사용자가 커맨드를 실행할 자격**을 봇이 판단하지 않는다는 뜻이고, 여기서 확인하는 것은 **봇 자신이 그 채널에서 동작 가능한지**다.
- **설정 삭제는 자동완성 목록에서 선택한다.** 원본 채널이 삭제된 고아 설정도 목록에 노출되어 정리할 수 있다. 채널 피커 방식은 삭제된 채널을 선택할 수 없어 이런 설정을 영구히 남긴다.
- **모든 `/setting` 응답은 ephemeral(호출자에게만 표시)이다.** 설정 작업 결과가 채널에 남을 이유가 없다.

### 4.2.1 설정 저장소 설계

**채택안: JSON 파일 저장소**

- 저장 대상 데이터(서버별 모니터링/출력 채널, 타겟 언어, 출력 채널별 Webhook 캐시 등)는 총량이 수 KB 수준이고, 쓰기 빈도도 관리자가 설정을 변경할 때뿐으로 극히 낮다. 따라서 인덱스·트랜잭션·쿼리 최적화가 필요한 수준이 아니다. (번역 API 키는 4.6에 따라 config.json이 아닌 `.env`에 전역으로 보관하므로 이 저장소의 대상이 아니다.)
- 이에 따라 별도 DB 없이 **JSON 파일 기반 저장소**를 채택한다. 봇 구동 시 파일을 읽어 메모리에 로드하고, 슬래시 커맨드로 설정이 변경될 때만 파일에 다시 기록(write-through)하는 방식이다.
- 채택 이유:
  - 데이터 규모·쓰기 빈도 대비 SQLite가 제공하는 이점(인덱스, 트랜잭션, 쿼리)이 실질적으로 필요하지 않음
  - `better-sqlite3`는 네이티브 모듈이라 설치 시 컴파일이 필요한데, GCP e2-micro(RAM 약 1GB)에서는 `npm install` 단계에서 메모리 부족으로 실패하는 사례가 흔해 배포 리스크가 있음
  - 별도 의존성 없이 Node.js 내장 `fs` 모듈만으로 구현 가능하여 코드와 배포가 단순해짐
  - 설정 파일을 사람이 직접 열어보고 수정할 수 있어, 장애 상황에서의 디버깅·수동 복구가 쉬움
- 배제한 대안:
  - **RDBMS(MySQL, PostgreSQL) / MongoDB**: 별도 서버 프로세스가 필요해 e2-micro의 메모리 여력을 초과함
  - **SQLite**: 위 사유로 이번 규모에는 과설계로 판단. 다만 향후 번역 이력·사용량 통계 등 조회 성능이 필요한 데이터가 추가되면 재검토
  - **env 파일만 사용**: 슬래시 커맨드로 실시간 설정 변경이 불가능해지고, 변경할 때마다 SSH 접속과 프로세스 재시작이 필요하여 운영 편의성이 크게 떨어짐
- 고려사항 및 한계:
  - 동시 쓰기 시 파일 손상을 방지하기 위해, 쓰기는 임시 파일에 기록 후 `rename`으로 교체하는 원자적 쓰기(atomic write) 방식으로 구현
  - 백업은 클라우드 업로드 없이 **로컬 로테이션 백업만** 둔다. 원자적 쓰기로 교체하기 직전에 기존 `config.json`을 `config.json.bak`으로 복사해두고, 로드 시 파일 손상이 감지되면 `.bak`으로 폴백한다. VM 디스크 자체의 손상/삭제까지는 대응하지 않는다(별도 클라우드 백업은 이번 범위에서 다루지 않음).
  - `config.json`에는 4.4의 Webhook 토큰이 저장된다. 이는 자격증명이므로 `.gitignore` 필수이며 배포 서버에서 `chmod 600`으로 보호한다
  - 향후 봇이 여러 인스턴스로 수평 확장되거나 데이터가 커질 경우, SQLite 또는 클라우드 매니지드 DB로의 전환을 검토

### 4.3 동작 흐름
1. 관리자가 모니터링 채널, 출력 채널, 타겟 언어를 설정으로 등록
2. 봇이 모니터링 채널의 메시지 이벤트를 상시 수신(listen)
3. 새 메시지 감지 시 원문 언어 판별
4. 타겟 언어와 다를 경우 번역 API 호출 (우선순위에 따른 순차 시도)
5. 번역 결과를 출력 채널에 Webhook을 통해 원 발신자 명의로 게시 (원문 링크 포함)

### 4.4 발신자 표시 (Webhook 기반)
- 번역된 메시지는 봇이 아닌 원 메시지 작성자의 이름과 프로필 사진으로 표시되도록 한다.
- 디스코드의 Webhook 기능을 활용하여 구현하며, 서버 내 Webhook 생성 및 관리가 필요하다.
- 기술적 고려사항:
  - 채널별(출력 채널 기준) Webhook을 사전에 생성/캐싱하여 재사용
  - 사용자 닉네임/아바타 URL을 Webhook 메시지 전송 시 파라미터로 전달
  - 원문에 첨부파일(이미지 등)이 있으면 URL을 그대로 Webhook 메시지에 전달한다. 멘션(`<@id>`)이나 커스텀 이모지는 별도 치환 없이 번역 API 호출 텍스트에 그대로 포함시켜 API의 처리 방식에 맡긴다.
  - 원문 또는 번역 결과가 디스코드 메시지 길이 제한(2000자)을 초과하면 2000자 단위로 잘라 같은 Webhook으로 연속 메시지를 전송한다. 원문 링크(4.5)는 마지막 조각에만 첨부한다.

### 4.5 원문 메시지 링크 삽입
- 번역된 메시지 내에 원본 메시지로 바로 이동할 수 있는 링크를 포함한다.
- 링크 형식: `https://discord.com/channels/{server_id}/{channel_id}/{message_id}`
- 표시 방식 예시: 번역문 하단에 "🔗 원문 보기" 형태의 링크 첨부

### 4.6 번역 API 우선순위 및 Failover (전역 고정, 길드별 등록 아님)
- 지원하는 번역 API는 **DeepL, Papago 두 개**로 한정한다 (Google Translate는 v1 범위에서 제외).
- 이 봇은 봇 운영자가 직접 관리하는 서버(들)에만 설치되는 것을 전제로 하므로, 서버(길드)마다 다른 API 키를 등록하는 멀티 테넌트 구조는 필요하지 않다. 대신 봇 운영자가 발급받은 키를 **전역으로 공용 사용**한다.
- 번역 API 키는 config.json이 아니라 **`.env`에 전역으로 보관**한다 (`DEEPL_API_KEY`, `PAPAGO_CLIENT_ID`, `PAPAGO_CLIENT_SECRET`). 슬래시 커맨드로 키를 등록/조회하는 기능은 두지 않는다.
- 우선순위(`deepl` → `papago`)는 서버별로 다르게 설정할 필요가 없으므로 **코드 상수로 고정**한다. 슬래시 커맨드로 우선순위를 바꾸는 기능은 두지 않는다.
- 동작 방식:
  - 1순위 API로 번역 요청 → 실패(오류, 쿼터 초과, 타임아웃 등) 시 다음 순위 API로 자동 전환(failover)
  - 모든 API가 실패할 경우 사용자에게 번역 실패 메시지 안내
- 각 제공자의 정확한 무료/유료 쿼터 수치는 시간이 지나면 바뀌는 외부 정보이므로 이 문서에 못박지 않는다. 키 발급 시점에 DeepL/Papago 콘솔에서 직접 확인한다.

### 4.7 출력 채널 접근 제어 (디스코드 자체 채널 권한 활용, 봇 관리 범위 아님)
- 번역 결과가 게시되는 출력 채널이 타겟 언어 사용자에게만 보이도록 하는 것은 **봇의 기능이 아니라, 디스코드 자체의 채널 권한(Role 기반 View Channel 권한) 기능**을 통해 서버 관리자가 직접 설정하는 영역이다.
- 관리자는 디스코드 서버 설정에서 출력 채널의 권한을 다음과 같이 구성한다 (봇과 무관하게, 디스코드 클라이언트에서 직접 설정):
  - `@everyone` 역할에 대해 해당 채널의 "채널 보기(View Channel)" 권한을 거부(Deny)
  - 원하는 언어 역할(예: "한국어 사용자")에 대해서만 "채널 보기" 권한을 허용(Allow)
- 봇은 이 채널에 **메시지를 전송하는 역할만** 수행하며, 채널을 누가 볼 수 있는지에는 관여하지 않는다. 즉, 봇은 어떤 채널이 어떤 역할에게만 보이도록 설정되어 있는지 알 필요도, 검증할 필요도 없다.
- 따라서 슬래시 커맨드 설정에는 "대상역할" 같은 파라미터가 필요 없으며, 관리자가 출력 채널을 지정할 때 그 채널의 열람 권한은 디스코드에서 별도로 미리 구성해두면 된다.
- 참고(권장 운영 순서): ① 관리자가 디스코드에서 언어별 역할과 비공개 채널을 먼저 만들고 채널 권한을 설정 → ② 그 채널을 봇의 슬래시 커맨드로 출력 채널로 등록

### 5.1 조사 결과 요약 (2026년 7월 기준)

| 리전 제한 | us-west1, us-central1, us-east1 중 택1 | 홈 리전(가입 시 선택한 리전)에 한정 | 제한 없음 (단, 상시 무료 아님) |

> 참고: Azure는 B1s VM을 계정 생성 후 12개월 동안만 무료로 제공하며, 그 이후에는 자동으로 유료 과금이 시작된다. 즉 Azure에는 영구적으로 무료인 VM이 없으므로, "Always Free" 조건을 요구하는 본 프로젝트의 호스팅 후보에서는 제외한다.

### 5.2 결론 및 권장안
- **1순위 후보: GCP e2-micro**
  - 기존에 운영 중인 `reaction-summary-bot`과 동일한 환경(pm2 + ts-node)을 그대로 재사용할 수 있어 운영 부담이 적음
  - 다만 RAM이 약 1GB로 매우 제한적이므로, 번역 봇처럼 다수의 메시지 이벤트를 동시에 처리해야 하는 경우 메모리 사용량 모니터링이 필요
  - 월 1GB egress 제한을 넘지 않도록 로깅/트래픽 최적화 필요
- **2순위 후보: Oracle Cloud Always Free (Ampere A1 Flex 또는 AMD Micro)**
  - 2026년 6월 기준 Ampere A1 Flex는 2 OCPU / 12GB RAM으로 제공되며, GCP e2-micro보다 훨씬 여유로운 사양과 월 10TB egress를 제공
  - 단, ARM 아키텍처이므로 Node.js 네이티브 모듈(예: 일부 이미지/오디오 처리 라이브러리) 호환성을 사전에 확인해야 함
  - 계정 신용카드 등록이 필요하고, 리전별 용량 부족으로 인스턴스 생성이 지연되는 사례가 보고되고 있어 안정성 측면에서 리스크가 있음
- **제외: Azure**
  - B1s 무료 제공이 12개월로 한정되어 있어 "Always Free" 요건을 충족하지 못함. 장기 운영을 전제로 하는 본 봇에는 부적합

### 5.3 최종 방향
- **GCP e2-micro**를 호스팅 환경으로 채택하고, 기존 `reaction-summary-bot`과 동일한 방식(pm2 + ts-node)으로 배포한다.
- 다른 클라우드로의 이전은 사전 계획으로 다루지 않는다. 리소스 한계(RAM/egress)에 실제로 부딪히는 시점이 오면 그때 재검토한다.

## 6. 권한 및 봇 계정 설정

두 가지를 구분해서 이해할 필요가 있다: (1) 서버 내 **사용자**가 봇에게 무엇을 할 수 있는지(6.1, 디스코드 명령어 권한 설정 레벨), (2) **봇 계정 자체**가 디스코드 API 상에서 무엇을 할 수 있는지(6.2, 봇 설치/설정 레벨).

### 6.1 사용자 권한 체계

- 본 봇이 실제로 관리하는 권한은 한 가지뿐이다: **누가 봇의 슬래시 커맨드(`/setting register` 등)를 실행해서 설정값(모니터링/출력 채널, 타겟 언어)을 등록·변경할 수 있는가**이다.
- 이 실행 권한은 서버 관리자(Administrator) 전체 권한으로 고정하지 않고, **디스코드가 자체 제공하는 "명령어별 권한 설정(Application Command Permissions)" 기능을 통해 서버마다 원하는 특정 역할로 지정**할 수 있도록 한다.
  - 서버 관리자는 디스코드 클라이언트의 **서버 설정 → 연동(Integrations) → 해당 봇 앱 → 명령어 권한** 메뉴에서, `/setting` 계열 명령어에 대해 사용 가능한 역할(예: "봇 관리자", "번역 운영팀" 등 서버마다 자유롭게 정한 역할)을 직접 지정한다.
  - 즉 명령어 사용 권한을 부여받기 위해 서버 전체 관리자 권한(ADMINISTRATOR)이 꼭 필요한 것은 아니며, 서버 관리자가 위임한 특정 역할만 가지고 있어도 설정을 등록/변경할 수 있다.
- 이 방식의 장점:
  - 봇 코드에서 역할 ID를 별도로 저장하거나 검증할 필요 없이, 디스코드 자체 UI에서 서버 관리자가 직접 위임 대상을 관리
  - 서버 전체 관리자 권한을 내주지 않고도, 봇 설정 권한만 세밀하게 특정 역할에 위임 가능
  - 서버의 역할 구성이 바뀌어도 봇 배포와 무관하게 Integrations 설정에서 즉시 재구성 가능
- 봇을 슬래시 커맨드로 등록할 때는 기본 권한(default member permissions)을 `Manage Server` 수준으로 설정해두고, 실제 최종 사용 권한은 각 서버의 관리자가 위 Integrations 설정에서 원하는 역할로 조정하도록 안내한다.
- 출력 채널을 누가 볼 수 있는지(4.7 참고)는 디스코드 자체 채널 권한 기능으로, **봇과 무관하게 서버 관리자가 직접 관리**한다. 봇은 이에 관여하지 않으며 별도의 검증도 수행하지 않는다.
- 원본(모니터링) 채널은 별도 제한 없이 기존 서버 권한 체계를 그대로 따른다.

### 6.2 봇 계정 권한 및 인텐트 (Discord Developer Portal 설정)

Discord Developer Portal에서 봇 생성 및 토큰 발급 시, 앞서 정의한 기능들이 동작하기 위해 아래 권한/설정을 반드시 체크해야 한다.

#### Privileged Gateway Intents (반드시 활성화)
- **MESSAGE CONTENT INTENT**: 모니터링 채널의 메시지 원문을 읽어 번역하기 위해 필수. 이 인텐트가 꺼져 있으면 메시지 내용 자체를 수신할 수 없다.
- **SERVER MEMBERS INTENT**: 명령어 실행 권한 자체는 6.1에서 설명한 디스코드 자체 명령어 권한 설정으로 걸러지므로 필수는 아니지만, 향후 멤버 정보 조회가 필요한 기능 확장에 대비해 활성화를 권장한다.

#### OAuth2 스코프 (봇 초대 링크 생성 시)
- `bot`: 봇 계정으로 서버에 참여
- `applications.commands`: 슬래시 커맨드(`/`) 등록 및 사용을 위해 필수

#### 봇 권한(Bot Permissions)
| 권한 | 용도 |
|---|---|
| Send Messages | 출력 채널에 번역 메시지 게시 |
| Manage Webhooks | 4.4 발신자 표시(Webhook 기반 번역 메시지 전송)를 위해 필수 |
| View Channels | 모니터링 채널 및 출력 채널 열람 |
| Read Message History | 원문 메시지 정보 조회(메시지 링크 생성 시 메시지 존재 확인 등)에 활용 |
| Embed Links | 번역 메시지를 임베드 형태로 구성할 경우 필요 |
| Use Slash Commands | 슬래시 커맨드 등록/응답 |

#### 기타 체크 사항
- 봇 토큰은 발급 즉시 안전한 곳(예: 환경변수, 시크릿 매니저)에 보관하고 절대 코드/저장소에 노출하지 않는다.
- 봇을 서버에 초대할 때는 위 OAuth2 스코프/봇 권한 항목이 반영된 초대 링크(OAuth2 URL Generator에서 생성)를 사용한다.
- Manage Webhooks 권한은 상대적으로 강력한 권한이므로, 봇 계정 자체의 역할 위치와 서버 내 노출 범위를 관리자가 인지하고 있어야 한다.
